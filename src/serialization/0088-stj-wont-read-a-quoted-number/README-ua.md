# #0088 - System.Text.Json не читає число в лапках

## 💥 Симптом

Інтеграція працювала на твоїх тестових payload-ах і кинула тієї миті, коли реальний
партнер надіслав трафік: `JsonException: The JSON value could not be converted to ...
Path: $.Quantity`. JSON коректний, поле присутнє - різниця лише в тому, що число
прийшло як `"3"`, а не `3`. Одна пара лапок - і весь об'єкт не десеріалізується.

## 🔍 Проблемний код

```csharp
string json = """{ "Quantity": "3", "UnitPrice": "9.99" }""";

var order = JsonSerializer.Deserialize<Order>(json); // 💥 "3" це рядок, не число

record Order(int Quantity, decimal UnitPrice);
```

## 🧠 Що насправді відбувається

`System.Text.Json` за замовчуванням суворий до JSON-типів: JSON-*рядок* (`"3"`) - це
не JSON-*число* (`3`), а конвертер для `int`/`decimal`-властивості приймає лише
number-токен. Зустрівши значення в лапках там, де очікується число, він не намагається
розпарсити текст - він кидає `JsonException`, і оскільки збій стається посеред об'єкта,
падає *вся* десеріалізація, не лише те одне поле. Newtonsoft.Json, навпаки, тихо парсить
`"3"` в `int`, тож код, змігрований із Newtonsoft (чи писаний тим, хто до нього звик),
несе припущення, що числа в лапках «просто працюють».

Хибне переконання - «це ж валідне число в JSON, тож воно зв'яжеться». Система типів JSON
розрізняє рядки й числа, а STJ суворо шанує цю різницю, а не приводить. Пастка в тому, що
формат на дроті часто поза твоїм контролем: `JSON.stringify` у JavaScript лишає числа
без лапок, але вручну зібрані payload-и, form-енкодери, `BigInt`/decimal-бібліотеки, що
стрінгіфаять заради точності, і багато партнерських API шлють числа рядками. Твої тести
використовують чистий числовий JSON і проходять; перший клієнт, що взяв числа в лапки,
кладе ендпоінт.

## ✅ Виправлення

Увімкни читання чисел із рядків через `JsonNumberHandling.AllowReadingFromString`.

```csharp
var options = new JsonSerializerOptions
{
    NumberHandling = JsonNumberHandling.AllowReadingFromString,
};

var order = JsonSerializer.Deserialize<Order>(json, options); // "3" -> 3
```

Повна версія в [Good.cs](Good.cs); помилка - у [Bad.cs](Bad.cs).

| Підхід | Коли він доречний |
|---|---|
| `NumberHandling = AllowReadingFromString` (глобально) | Джерело може брати будь-яке число в лапки - постав це раз на спільних `JsonSerializerOptions`, щоб кожна числова властивість терпіла значення в лапках. |
| `[JsonNumberHandling(...)]` на властивості/типі | У лапках лише деякі поля (decimal заради точності, ID) - анотуй лише їх, лишаючи решту суворою. |
| `AllowReadingFromString \| WriteAsString` | Треба round-trip - читати числа в лапках *і* писати їх назад у лапках (напр. зберегти точність `long`/`decimal` для JS-споживача). |
| Полагодь продюсера | Ти володієш обома кінцями - віддавай справжні JSON-числа, щоб жодна сторона не потребувала послабленого режиму; лишай лапки для значень, яким вони справді потрібні. |

## 😈 Ще гірший родич

Жорсткий `JsonException` принаймні спиняє погані дані на порозі - ти знаєш, що парсинг
впав. Тихіший родич - розбіжність *регістру*, де число без лапок і валідне, але ім'я
властивості не збігається, тож STJ лишає властивість дефолтною й не звітує про помилку
взагалі - `{"amount": 100}`, прив'язане до незбіжного `Amount`, дає тихий `0`,
замовлення, що «успішно» десеріалізувалось за нульовою ціною (див.
[0012-zero-priced-order](../0012-zero-priced-order/)). І `AllowReadingFromString` має
власне гостре ребро: він робить парсинг *поблажливішим*, тож справді покручене `"3abc"`
все одно кине, але порожній рядок `""` для nullable-числа тепер може зв'язатися так, як
ти не мав на думці - послабити типовий гейт це компроміс, не безкоштовний виграш.

## 🎓 Поглиблений нюанс

- **Це асиметрично за замовчуванням.** STJ *пише* числа без лапок і *читає* лише числа
  без лапок, поки ти не увімкнеш опцію; `AllowReadingFromString` змінює лише бік читання.
  Якщо споживачу потрібні числа в лапках на дроті, додай `WriteAsString` явно.
- **Збій - на весь об'єкт, не на поле.** Оскільки виняток обриває десеріалізацію, одне
  число в лапках валить увесь payload - ти не отримуєш частково заповнений об'єкт із лише
  цим полем дефолтним, ти не отримуєш нічого.
- **`JsonNumberHandling.Strict` - дефолт, а `AllowNamedFloatingPointLiterals` окремо.**
  Читання `"NaN"`/`"Infinity"` - це *інший* прапорець; дозвіл чисел у лапках не дозволяє
  `NaN` у лапках, тож змішування payload-ів із float-літералами потребує власної опції.

## 🔎 Як знайти у своїй кодовій базі

- Грепни `JsonSerializer.Deserialize`/`ReadFromJsonAsync` на DTO з числовими
  (`int`, `long`, `decimal`, `double`) властивостями, чий JSON приходить від зовнішнього
  партнера, браузерної форми чи системи, відомої тим, що стрінгіфаїть числа.
- Відтвори payload-ом, де числа в лапках (`"3"`, не `3`) - якщо кидає `JsonException: The
  JSON value could not be converted`, це воно.
- З боку симптомів: ендпоінт, що проходить внутрішні тести, але 400/500 для конкретного
  клієнта, збої десеріалізації, що називають числовий `$.Path`, інтеграції, що зламались
  після переходу з Newtonsoft.Json на System.Text.Json.
- Вирішуй свідомо: послаб через `AllowReadingFromString`, де формат на дроті поза твоїм
  контролем, чи полагодь продюсера віддавати справжні JSON-числа, де ти ним володієш.

# #0072 - Сума, що завернулась

## 💥 Симптом

Рахунок на велике замовлення виходить набагато меншим - замовлення на `$49,999.50` виставлене як
`$7,049.83`. Ні помилки, ні попередження; арифметика тихо видала неправильне число, і система його
списала. Кількість і ціна обидві правильні, множення тривіальне, а проте сума - лише частка того,
що мала б бути (або, на інших входах, від'ємна). Гроші зникли між двома правильними числами і `*`.

## 🔍 Проблемний код

```csharp
int totalCents = quantity * unitPriceCents; // 💥 50_000 * 99_999 = 4_999_950_000, переповнює int, завертається у 704_982_704
```

## 🧠 Що насправді відбувається

Ціла арифметика в C# за замовчуванням виконується в контексті **unchecked**, і при переповненні вона
тихо завертається, а не падає. `quantity * unitPriceCents` рахується в `int`; коли справжній добуток
(4,999,950,000) перевищує `int.MaxValue` (2,147,483,647), результат завертається за модулем 2^32 аж
до 704,982,704 - меншого, додатного, цілком правдоподібного на вигляд числа. Обидва операнди влазять
в `int`; їхній добуток - ні, і ніщо тебе не попереджає, бо завертання тут - визначена поведінка мови,
а не помилка. Клієнту виставляють `$7,049.83` за замовлення на `$49,999.50`, і кожен рядок лога
виглядає нормально.

Хибне переконання: «якщо математика переповнилась, я отримаю виняток». Отримав би в контексті
`checked`; за замовчуванням - ні. Дефолт міняє безпеку на швидкість - `int.MaxValue + 1` це
`int.MinValue` - тож сума, що переросла `int`, стає тихо неправильною сумою, а не падінням.

## ✅ Виправлення

Зроби, щоб арифметика кидала, а не завертала - рахуй грошову математику в контексті `checked`, щоб
переповнення виринало як `OverflowException`, який ти зловиш і відхилиш, а не як неправильна сума,
яку ти спишеш:

```csharp
try
{
    int totalCents = checked(quantity * unitPriceCents); // кидає OverflowException при переповненні
    Charge(totalCents);
}
catch (OverflowException)
{
    Reject("сума замовлення перевищує підтримуваний діапазон"); // ніколи не білити завернуте число
}
```

Повна версія в [Good.cs](Good.cs); помилка - у [Bad.cs](Bad.cs).

| Підхід | Коли він доречний |
|---|---|
| `checked(...)` навколо арифметики | Гроші й лічильники, де неправильне число ніколи не має піти тихо - переповнення стає ловимим `OverflowException` на самій операції. |
| `<CheckForOverflowUnderflow>` для проєкту | Ти хочеш, щоб кидало *кожне* переповнення, а не лише ті місця, які ти згадав загорнути - найбезпечніший дефолт для біллінг/фінансового сервісу. |
| Рахувати в `long` (або `decimal`) | Значенню законно потрібен діапазон - `(long)quantity * unitPriceCents` його тримає; `decimal` для грошей, які ще й округлюєш і показуєш. Розширення несе число; `checked` стереже ті, що лишаєш в `int`. |
| Валідувати входи проти ліміту | Відхили замовлення, чиє `quantity * price` не влазить, ще до обчислення - падай із бізнес-повідомленням, а не арифметичним. |

## 😈 Ще гірший родич

Недоплата гучна заднім числом; завертання в *мінус* - гірше в моменті. `int.MaxValue + 1` це
`int.MinValue`, тож сума, що переповнює трохи за ліміт, може вийти великим від'ємним числом -
повернення коштів там, де ти хотів списання, баланс, що змінює знак, кількість, яка читається як
«винні клієнту». І переповнення за природою залежить від даних: множення правильне для кожного
замовлення в деві й тестах (малі кількості, малі ціни) і завертається першого ж разу, коли реальне
оптове замовлення перетне ~2.1 мільярда центів - саме те замовлення, що велике достатньо, аби
важити. `checked` кинув би на тому першому великому замовленні; без нього воно відправило
неправильне число, і лише звірка - через кілька днів - знаходить суму, яку не пояснює жоден рядок.

## 🎓 Поглиблений нюанс

- **`checked` / `unchecked` - лексичні, не глибокі.** `checked(expr)` покриває операції *в цьому
  виразі*, а не виклики, які він робить; множення всередині методу, який ти викликаєш, працює у
  власному (дефолтному `unchecked`) контексті того методу. Загортай саму арифметику, або став
  прапор на весь проєкт, а не далекого викликача.
- **Константне переповнення - помилка компіляції; рантаймне - ні.** `int x = int.MaxValue + 1;` (усі
  константи) не компілюється; те саме переповнення зі змінними тихо завертається під час виконання.
  Компілятор ловить те, що бачить, а решту постачає прод.
- **Кидають лише цілі `checked`-операції; плаваюча кома - ніколи.** Переповнення `int` / `long`
  кидає під `checked`; переповнення `double` дає `Infinity` і не кидає незалежно ні від чого. Якщо
  сума може бути величезною і дробовою, грошовий тип - це `decimal` (який *таки* кидає на
  переповненні), а не `double`.

## 🔎 Як знайти у своїй кодовій базі

- Грепни `int` (та `short`) арифметику над грошима, лічильниками чи розмірами, що можуть рости -
  `* price`, `* quantity`, `+= amount`, `Sum()` над `int` - і спитай, чи може *результат* перевищити
  ~2.1 мільярда.
- Увімкни `<CheckForOverflowUnderflow>true</CheckForOverflowUnderflow>` у фінансовому / біллінг
  проєкті (принаймні в Debug / CI), щоб тихі завертання стали падаючими тестами, тоді полагодь або
  явно `unchecked` ті місця, що навмисні.
- З боку симптомів: суми, набагато менші за очікувані, або від'ємні, для великих замовлень; розриви у
  звірці, яких не пояснює жодна позиція; значення, правильне для малих входів і неправильне для
  великих.
- Неси справді великі значення в `long` / `decimal`, а `int`-арифметику, яку лишаєш, загортай у
  `checked`, щоб переповнення кидало біля джерела, а не білило завернуте число.

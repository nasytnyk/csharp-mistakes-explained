# #0072 - Середина, що переповнилась

## 💥 Симптом

Бінарний пошук, що проходить усі тести, раптом повертає сміття - або кидає `IndexOutOfRange` -
на великому вході. Середина чи середнє опиняються *поза* двома значеннями, між якими мали б бути:
середина `[1.5млрд, 2.0млрд]` повертається від'ємним числом. Дані не пошкоджені, логіка читається
як у підручнику, а проте точка посередині - зовсім не посередині.

## 🔍 Проблемний код

```csharp
int mid = (low + high) / 2; // 💥 low + high переповнює int ще до ділення
```

## 🧠 Що насправді відбувається

Додавання `int` відбувається в `int` і тихо завертається при переповненні (дефолтний контекст
`unchecked`). Коли `low + high` перевищує `int.MaxValue` (близько 2.1 мільярда), сума завертається
у велике від'ємне число *до* того, як виконається ділення - тож `(1_500_000_000 + 2_000_000_000) / 2`
це не `1.75млрд`, а `-794_967_296 / 2 = -397_483_648`. Ділення чесно ділить навпіл число, яке вже
неправильне. Кожен операнд влазить в `int`; їхня *сума* - ні, і ніщо тебе не попереджає, бо
переповнення тут - визначена поведінка, а не помилка.

Хибне переконання: «обидва значення - валідні int, тож `(a + b) / 2` - валідний int». Результат -
так; проміжне `a + b` - пастка. Це саме той баг, що роками сидів у реалізаціях бінарного пошуку -
серед них у відомій бібліотеці й у безлічі підручників: правильний для малих діапазонів, тихо
зламаний тієї миті, коли індекси чи значення переростають половину діапазону `int`.

## ✅ Виправлення

Обчислюй зсув від `low`, а не суму обох кінців - `high - low` завжди влазить в `int`, коли обидва
невід'ємні й `low <= high`:

```csharp
int mid = low + (high - low) / 2; // без переповнення
```

Повна версія в [Good.cs](Good.cs); помилка - у [Bad.cs](Bad.cs).

| Підхід | Коли він доречний |
|---|---|
| `low + (high - low) / 2` | Стандартна середина двох упорядкованих невід'ємних int - `high - low` не може переповнитись, а результат збігається з `(a+b)/2` для кожного значення, де той спрацював би. |
| Розширити до `long` для суми | Значення можуть бути від'ємні чи невпорядковані - `(int)(((long)a + b) / 2)` рахує в 64 бітах, де сума влазить, тоді звужує результат (уже в межах). |
| Блок `checked` | Ти б радше впав, ніж завернувся - `checked((a + b) / 2)` кидає `OverflowException` на сумі, перетворюючи тиху неправильну відповідь на гучну й полагоджувану. |
| `long`-центи або `decimal` для середніх сум | Усереднення грошей у центах понад ~21 млн доларів теж переповнює `int` - бери `long`-центи чи `decimal` і явно вирішуй округлення «половинної» копійки. |

## 😈 Ще гірший родич

Середина - відомий випадок; те саме переповнення ховається в кожному «сума потім ділення».
`(a + b) / 2` для двох великих показів сенсорів, двох таймстемпів у секундах, двох балансів у центах -
кожне завертається тієї миті, коли *сума* перетинає `int.MaxValue`, задовго до того, як хоч один
операнд стане на вигляд великим. І воно тихе за конструкцією: операнди явно в межах, результат явно
в межах, поза межами лише невидиме проміжне - тож рев'ю бачить два валідні int і ділення й іде далі.
Гірше, воно залежить від даних: функція правильна роками на малих входах і падає першого ж разу, коли
прод підсуне два значення, чия сума перевалить за ~2.1 мільярда - саме тоді, коли числа нарешті
важать. Контекст `checked` змусив би це кинути, але ніхто не тягнеться до `checked` заради «просто
середнього». Те саме переповнення лежить в основі
[0050-the-widening-that-came-too-late](../0050-the-widening-that-came-too-late/): арифметика
фіксується у вузькому типі раніше, ніж ти цього хотів.

## 🎓 Поглиблений нюанс

- **Переповнення тихе, бо `unchecked` - це дефолт.** Арифметика C# завертається, якщо ти не увімкнеш
  `checked` (або `<CheckForOverflowUnderflow>` у проєкті), тож `int.MaxValue + 1` - це `int.MinValue`,
  а не виняток; баг із середнім - один із проявів цього глобального дефолту.
- **`high - low` безпечне лише коли `low <= high` й обидва невід'ємні.** Якщо `low` може перевищити
  `high`, або якесь із них від'ємне, `high - low` саме може переповнитись - тоді розширюй до `long`
  для суми, а не використовуй трюк із відніманням. Знай, який інваріант ти насправді тримаєш.
- **Та сама форма кусає множення й зсув.** `a * 2`, `a + b`, `1 << 31` переповнюють `int` задовго до
  того, як значення стане на вигляд великим; будь-яке проміжне, що переростає тип, завертається,
  навіть коли входи й кінцевий результат обидва в межах.

## 🔎 Як знайти у своїй кодовій базі

- Грепни `(low + high) / 2`, `(lo + hi) / 2`, `(left + right) / 2`, `(a + b) / 2` та
  `(start + end) / 2` - ідіома середини/середнього над `int` - це і є форма; заміни на
  `low + (high - low) / 2`.
- Дивись на бінарні пошуки, бісекцію, півоти quicksort/mergesort і будь-яке середнє двох `int`, що
  можуть вирости великими (id, таймстемпи-в-секундах, центи) - саме там сума реалістично перетинає
  `int.MaxValue`.
- З боку симптомів: пошук чи середнє, правильні для малих входів і неправильні (або `IndexOutOfRange`)
  для великих; «середнє» значення, що від'ємне або поза своїми кінцями.
- Щоб падало гучно, а не тихо, загорни арифметику в `checked` або ввімкни перевірку переповнення для
  проєкту, щоб завертання кидало, а не брехало.

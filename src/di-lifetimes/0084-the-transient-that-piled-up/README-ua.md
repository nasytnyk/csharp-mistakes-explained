# #0084 - Transient, що накопичився

## 💥 Симптом

Довгоживучий сервіс - воркер, hosted-фонова робота, консюмер черги - росте в пам'яті
й відкритих хендлах, що довше працює, а рестарт «лагодить» це. Залежність
зареєстрована як `Transient`, що всі читають як «створюється, використовується,
викидається», тож це останнє, на що падає підозра. А проте кожна робота відкриває ще
одну `DbSession`, і жодна не закривається, поки процес не вийде.

## 🔍 Проблемний код

```csharp
var provider = new ServiceCollection()
    .AddTransient<DbSession>()
    .BuildServiceProvider();

for (int job = 0; job < jobs; job++)
{
    var session = provider.GetRequiredService<DbSession>(); // 💥 резолв із кореня
    session.Run(job);
    // session виходить з області тут - але контейнер досі його тримає
}
```

## 🧠 Що насправді відбувається

DI-контейнер володіє часом життя кожного `IDisposable`, який створює, і dispose-ить їх
**коли dispose-иться провайдер-власник** - не коли твоя локальна змінна виходить з
області, не на наступному GC. Щоб це зробити, він тримає посилання на кожен виданий
disposable-екземпляр. `Transient` керує тим, як *часто* створюється новий екземпляр
(на кожен резолв), але не тим, *коли* його звільнено: це прив'язано до провайдера,
через який пройшов резолв. Резолвиш із кореневого провайдера - і власник це корінь,
чий час життя - увесь застосунок, - тож контейнер тримає кожну сесію до shutdown, і
резолв-на-роботу стає витоком-на-роботу.

Хибне переконання - «transient означає короткоживучий, тож він сам себе прибере».
*Створення* transient дешеве й часте, але його *звільнення* відкладене до scope-власника,
і якщо цей scope - корінь застосунку, «відкладене» означає «при виході процесу».
Екземпляр і GC не збере - саме тому, що контейнер досі тримає його, щоб dispose-нути, -
тож профайлер пам'яті показує об'єкти живими й вкоріненими, що виглядає як витік
контейнера, а не як вибір неправильного власника на місці резолву.

## ✅ Виправлення

Створи scope на кожну одиницю роботи й резолви з нього. Dispose scope dispose-ить усе,
створене в ньому.

```csharp
for (int job = 0; job < jobs; job++)
{
    using var scope = provider.CreateScope();
    var session = scope.ServiceProvider.GetRequiredService<DbSession>();
    session.Run(job);
} // scope dispose-нуто -> сесію dispose-нуто тут
```

Повна версія в [Good.cs](Good.cs); помилка - у [Bad.cs](Bad.cs).

| Підхід | Коли він доречний |
|---|---|
| Scope на одиницю роботи | Загальний фікс - загорни кожну роботу/запит/повідомлення в `using var scope = provider.CreateScope()` і резолви зі scope, щоб його disposable вмирали разом з ним. |
| Хай scope володіє фреймворк | Шаблони ASP.NET Core / Worker уже відкривають scope на запит чи ітерацію `ExecuteAsync` - інжектуй у *scoped*-компонент і ніколи не резолви з кореня сам. |
| Фабрика для disposable | Залежність створюється на вимогу посеред методу - інжектуй `Func<DbSession>` чи `IDbSessionFactory` і загортай кожен `using var session = factory()` сам, володіючи disposal явно. |
| Не роби його transient IDisposable взагалі | Пул чи спільний ресурс - зареєструй так, щоб контейнер створював один (singleton/пул), а не новий disposable на кожен резолв, який треба відстежувати й звільняти. |

## 😈 Ще гірший родич

Накопичення transient до shutdown - це *повільний* витік: щоб зашкодити, потрібен
довгоживучий процес. Різкіший збій - інжект того самого transient `IDisposable` у
**singleton**: singleton будується раз і тримає той один екземпляр увесь застосунок,
тож «transient»-залежність тихо підвищується до часу життя, на який її не проєктували -
з'єднання-на-запит тепер спільне для всіх потоків, чи stateful-хелпер, що мав бути
одноразовим, тепер живе вічно (пастка «singleton захоплює коротший час життя»,
дзеркало [0022-the-captive-scoped](../0022-the-captive-scoped/)). А зворотне кусає в
ASP.NET Core: резолвни *scoped*-сервіс прямо з кореневого провайдера - і отримаєш
`InvalidOperationException: Cannot resolve scoped service ... from root provider` -
фреймворк його забороняє, тоді як витік transient-з-кореня дозволяє тихо.

## 🎓 Поглиблений нюанс

- **Відстежуються лише `IDisposable`-transient.** Transient без `IDisposable` (чи
  `IAsyncDisposable`) створюється й справді забувається - GC збирає його нормально.
  Відстеження, а отже й витік, існує саме тому, що контейнер пообіцяв викликати
  `Dispose`, а єдиний спосіб дотримати обіцянку - тримати посилання, поки не скінчиться
  scope-власник.
- **`IAsyncDisposable` потребує async-шляху disposal.** Якщо transient реалізує
  `IAsyncDisposable`, dispose-ь scope через `await scope.DisposeAsync()` (чи використовуй
  `AsyncServiceScope`); синхронний dispose може кинути `InvalidOperationException` для
  async-only disposable.
- **`using`/фабрика, якими володієш ти, повністю оминають відстеження контейнером.** Коли
  пишеш `using var session = factory()`, *ти* dispose-иш його на закривальній дужці, і
  контейнер його не тримає - тому явна фабрика це правильний інструмент для disposable,
  створеного глибоко в методі, а не на етапі композиції.

## 🔎 Як знайти у своїй кодовій базі

- Грепни `GetService`/`GetRequiredService`, викликані на кореневому `IServiceProvider`
  (чи на `IServiceProvider`, інжектованому в singleton) для типу, що реалізує
  `IDisposable` - кожен виклик додає екземпляр, який корінь триматиме до shutdown.
- Дивись на довгі цикли - фонові воркери, консюмери, таймери - що резолвлять disposable
  на ітерацію без відкриття scope.
- З боку симптомів: пам'ять і кількість хендлів, що ростуть з аптаймом і скидаються на
  рестарті, disposable, чий `Dispose` біжить лише на shutdown (чи ніколи, якщо провайдер
  ніколи не dispose-иться), профілі з багатьма живими екземплярами, вкоріненими сервіс-
  провайдером.
- Відкривай scope на одиницю роботи (чи інжектуй фабрику), щоб кожен transient-disposable
  мав короткоживучого власника, і лишай резолви з кореня для singleton-ів.

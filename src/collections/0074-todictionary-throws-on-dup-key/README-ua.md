# #0074 - ToDictionary кидає на дублі ключа

## 💥 Симптом

Сервіс, що чудово стартує в деві, падає на старті в проді з
`ArgumentException: An item with the same key has already been added.` Код щойно збудував lookup -
`things.ToDictionary(t => t.Id)` - з даних, у яких цього разу два рядки поділили один id. Жоден id
не був невалідним; просто два виявились рівними, і `ToDictionary` відмовляється продовжувати.

## 🔍 Проблемний код

```csharp
var priceBySku = feed.ToDictionary(p => p.Sku, p => p.Price); // 💥 кидає, якщо якийсь SKU повториться
```

## 🧠 Що насправді відбувається

`ToDictionary` будує `Dictionary`, чиї ключі унікальні - тож першого ж разу, коли селектор ключа
видасть ключ, який він уже бачив, `ToDictionary` кидає `ArgumentException`, а не обирає переможця.
`Dictionary.Add` та ініціалізатор `{ [k] = v }` поводяться так само: вони стверджують унікальність і
гучно падають на колізії. Немає перевантаження `ToDictionary` на кшталт «останній виграє» чи
«перший виграє»; унікальність - це передумова, а її порушення - виняток, не злиття.

Хибне переконання: «цей ключ унікальний, тож можна індексувати за ним». Він унікальний у зразкових
даних і фікстурах; прод постачає той рядок, що ні - дубльований SKU з корекції фіду, два користувачі
з однією поштою, зовнішній id, що виявився один-до-багатьох. `ToDictionary` не порахував неправильну
відповідь; він оголосив твоє припущення про унікальність хибним - у найгірший момент.

## ✅ Виправлення

Виріши, що *означає* дубль, і візьми операцію, яка це виражає - згрупуй, щоб лишити всі, або зведи
до одного навмисно:

```csharp
// останній рядок виграє за ключем:
var priceBySku = feed.GroupBy(p => p.Sku).ToDictionary(g => g.Key, g => g.Last().Price);

// лишити кожен рядок за ключем (lookup один-до-багатьох):
ILookup<string, decimal> pricesBySku = feed.ToLookup(p => p.Sku, p => p.Price);
```

Повна версія в [Good.cs](Good.cs); помилка - у [Bad.cs](Bad.cs).

| Підхід | Коли він доречний |
|---|---|
| `GroupBy(key).ToDictionary(g => g.Key, g => g.Last())` | Дублі реальні й один має виграти - найновіший, найбільший, як скаже `Last` / `Max` / `OrderBy`. Зроби tiebreak явним. |
| `ToLookup(key)` | Багато значень на ключ - це і є суть (замовлення на клієнта, ціни на SKU) - `ILookup` це словник груп, а відсутній ключ повертає порожню послідовність, не виняток. |
| `dict[key] = value` у циклі | Рукописний last-wins - індексатор перезаписує тихо там, де `Add` / `ToDictionary` кидають. Обирай навмисно, коли перезапис і є наміром. |
| Лишити `ToDictionary` і хай кидає | Ключ справді має бути унікальним, а дубль - це баг даних, який ти хочеш висвітлити - тоді виняток правильний (він навіть називає ключ-колізію). |

## 😈 Ще гірший родич

Кидок - чесна половина родини; *тихі* члени гірші. Індексатор `dict[key] = value`, до якого
тягнуться як до «фіксу», не кидає ніколи - він перезаписує, тож дубль тихо викидає кожен попередній
рядок, і ти лишаєшся тільки з останнім, без жодного знаку, що дані впали. А `Distinct()`, докинутий,
щоб «дедуплікувати перед ToDictionary», прибирає рядки за *повною рівністю значень*, не за ключем -
тож два рядки з тим самим SKU, але різними цінами, обидва виживають, і `ToDictionary` усе одно кидає,
а два ідентичні рядки тихо схлопуються в один, ховаючи справжній дубль, який тобі треба було
побачити. Той самий дубль ключа, три результати: `ToDictionary` падає, індексатор лишає один без
слова, `Distinct` міняє, які рядки існують - і лише падіння каже правду.

## 🎓 Поглиблений нюанс

- **`Add` кидає, індексатор перезаписує - за задумом.** `dict.Add(k, v)` стверджує, що ключ новий;
  `dict[k] = v` робить upsert. `ToDictionary` та ініціалізатор `{ [k]=v }` обидва мають семантику
  `Add`, тому й кидають на колізії.
- **Компаратор ключа вирішує, що таке «дубль».** `ToDictionary(k, comparer)` бере переданий
  `IEqualityComparer`; ключі, *ординально* різні, можуть зіткнутись під регістро-нечутливим
  компаратором (`"SKU"` і `"sku"`), перетворивши «унікальний» ключ на дубль - або навпаки. Передай
  компаратор, що відповідає твоєму означенню «те саме».
- **`ToLookup` жадібний і терпить null-ключ.** На відміну від `GroupBy` (відкладеного), `ToLookup`
  виконується одразу й *дозволяє* null-ключ (як окрему групу), тоді як `ToDictionary` кидає на
  null-ключі. Якщо ключі можуть бути null, ця різниця важить.

## 🔎 Як знайти у своїй кодовій базі

- Грепни `.ToDictionary(` та `Dictionary.Add(` і спитай, чи може ключ *взагалі* повторитись у
  реальних даних - фід, імпорт, join, введені користувачем значення - не лише у фікстурах.
- Бери `ToLookup`, коли багато-на-ключ законно, і `GroupBy(...).ToDictionary(...)` з явним tiebreak,
  коли один має виграти; лишай голий `ToDictionary` для ключів, що мусять бути унікальні, і де дубль
  - баг, вартий падіння.
- З боку симптомів: `ArgumentException: An item with the same key has already been added` на старті
  чи першому запиті; lookup, що «губить» рядки (тихий перезапис через індексатор); `Distinct`, що не
  зупинив кидок.
- Якщо дубль - це помилка даних, висвіти її ясно: виняток уже називає ключ-колізію (`Key: A-1`);
  злови його на місці побудови й додай, з якого фіду чи імпорту він прийшов.

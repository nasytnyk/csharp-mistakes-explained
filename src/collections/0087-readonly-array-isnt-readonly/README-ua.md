# #0087 - readonly-масив не readonly

## 💥 Симптом

Спільна таблиця дефолтів - затримки повторів, податкові ставки, дозволені статуси -
оголошена `static readonly`, тож читається як незмінна й недоторканна. Потім один
запит «підправляє» запис для себе - і кожен *інший* запит тихо починає бачити
підправлене значення. Ніщо не перепризначило поле, винятку не було, а ключове слово
`readonly` ось воно - і все ж глобальні дефолти переписані для всіх.

## 🔍 Проблемний код

```csharp
static class Config
{
    public static readonly int[] RetryDelays = { 1, 2, 4 }; // «незмінні» дефолти
}

Config.RetryDelays[0] = 30; // 💥 компілюється - readonly захищає посилання, не елементи
```

## 🧠 Що насправді відбувається

`readonly` на полі означає, що *поле* не можна перепризначити після конструювання -
`Config.RetryDelays = somethingElse` це помилка компіляції. Про об'єкт, на який поле
вказує, воно не каже нічого. Масив - мутабельний reference-тип, тож `RetryDelays[0] =
30` не чіпає поле взагалі; воно тягнеться крізь (незмінне) посилання й пише у сховище
масиву. Той один екземпляр масиву спільний для кожного читача `Config.RetryDelays`,
тож одне присвоєння елемента редагує дефолти на весь процес.

Хибне переконання - «`readonly` робить це незмінним». `readonly` заморожує рівно одне -
посилання в полі - і заморожує його проти перепризначення, не проти мутації того, на що
воно вказує. Для value-типу (`readonly int Max`) це випадково означає повну
незмінність - звідси й впевненість; але для будь-якого reference-типу - масив,
`List<T>`, мутабельний клас - `readonly` замикає двері й лишає кожне вікно відчиненим.
`public static readonly` масив - тому один із найоманливіших спільних мутабельних
глобалів у мові: виглядає як константа, а поводиться як публічне поле, яке будь-хто може
переписати.

## ✅ Виправлення

Віддавай щось, що не має in-place-сеттера, тож присвоєння елемента навіть не
скомпілюється, а «підправлення» мусить будувати власну копію.

```csharp
using System.Collections.Immutable;

static class Config
{
    public static readonly ImmutableArray<int> RetryDelays = ImmutableArray.Create(1, 2, 4);
}

ImmutableArray<int> burst = Config.RetryDelays.SetItem(0, 30); // новий масив; спільний недоторканий
```

Повна версія в [Good.cs](Good.cs); помилка - у [Bad.cs](Bad.cs).

| Підхід | Коли він доречний |
|---|---|
| `ImmutableArray<T>` / `ImmutableList<T>` | Спільні дефолти, що ніколи не мають мінятися на місці - присвоєння не компілюється, а `SetItem`/`Add` повертають новий екземпляр, тож підправлення викликача це його власна копія. |
| `ReadOnlyCollection<T>` / `IReadOnlyList<T>` | Тримаєш приватний мутабельний список і віддаєш read-only *в'ю* - викликачі не можуть `Add`/set крізь в'ю (хоча ти сам можеш навмисне мутувати бекінг-список). |
| Віддавай копію | Викликачам законно треба мутувати результат - повертай `array.ToArray()` / `list.ToList()`, щоб кожен отримав приватну копію, а джерело лишалось безпечним. |
| Метод, не поле | Значення обчислюються чи per-call - `GetRetryDelays()`, що повертає свіжий масив щоразу, взагалі прибирає спільний екземпляр. |

## 😈 Ще гірший родич

`int[]` принаймні показує мутацію на елементі, який ти записав. Та сама пастка
«`readonly` не глибокий» ховається тихіше на рівень усередину: `readonly`-поле, що
тримає *мутабельний об'єкт* (`readonly Settings Config` із сеттер-властивостями чи
`readonly List<Order> Pending`), дозволяє викликачам міняти стан об'єкта - `Config.Timeout
= 0`, `Pending.Clear()` - поки поле лишається `readonly`, а компілятор мовчить. І `const`
теж не рятує, бо `const`-масив чи об'єкт узагалі не оголосити - лише compile-time
примітиви - тож `static readonly` це інструмент, по який тягнуться саме там, де він дає
найменше захисту. Дзеркальний баг - віддати той самий спільний масив крізь *геттер*, що
повертає його напряму, тож навіть тип, що виглядає інкапсульованим, зливає writable-хендл
до внутрішнього стану.

## 🎓 Поглиблений нюанс

- **`readonly` неглибокий за визначенням.** Він обмежує прив'язку поля, не вміст
  об'єкта - у C# немає транзитивного/глибокого `readonly`. Глибина йде лише від
  *типу*, що є незмінним (`ImmutableArray<T>`, `readonly record struct`, клас без
  сеттерів), не від модифікатора.
- **`ImmutableArray<T>` це struct-обгортка над масивом.** Його незмінність справжня,
  бо він не має мутаторів і копіює при зміні - але зауваж: *default* `ImmutableArray<T>`
  (ніколи не ініціалізований) це `default`, і доступ до нього кидає `NullReferenceException`;
  ініціалізуй його (як робить поле), а не лишай `default`.
- **`readonly` таки допомагає проти одного реального бага.** Він запобігає випадковому
  перепризначенню поля (заміні всього масиву на інший), що варте мати - просто це не є і
  ніколи не було твердженням про елементи.

## 🔎 Як знайти у своїй кодовій базі

- Грепни `static readonly` (і `readonly`) поля, чий тип - масив, `List<T>`,
  `Dictionary<,>` чи будь-який мутабельний клас - кожне це спільний об'єкт, який
  `readonly` не захищає від мутації.
- Шукай записи елементів/`Add`/`Clear`/властивостей крізь такі поля, особливо у
  request-scoped чи per-item шляхах, що «підправляють» спільний дефолт.
- З боку симптомів: глобальний дефолт, що дрейфує з часом, значення, що різняться між
  запитами без коду, який їх перепризначує, баги «хтось змінив конфіг», що
  відтворюються лише після певної попередньої операції.
- Віддавай спільні дані, що не мають мінятися, як `ImmutableArray<T>`/`IReadOnlyList<T>`,
  чи роздавай копії; лишай `readonly` на мутабельному reference-типі для випадків, де
  in-place-мутація справді задумана.

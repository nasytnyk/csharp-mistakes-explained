# #0077 - finally виконується не завжди

## 💥 Симптом

Єдина гарантія, на яку всі спираються - «хоч би як цей блок завершився, `finally`
виконається» - тихо виявляється не абсолютною. Батч скидає свій audit log, закриває
файл, звільняє блокування у `finally` - і одного дня прибирання просто не
стається: жодного винятку, жодної помилки, і код виходу `0`, що читається як успіх.
Прогін не лишив сліду, і ніщо не вказує чому.

## 🔍 Проблемний код

```csharp
void RunBatch()
{
    try
    {
        // ... обробка записів ...
        Environment.Exit(0); // 💥 завершує процес тут - finally не виконається
    }
    finally
    {
        FlushAuditLog(); // «гарантоване» прибирання - пропущене
    }
}
```

## 🧠 Що насправді відбувається

`finally` гарантований лише проти тих виходів, якими керує сама мова: падіння за
кінець блоку, `return`, `break`, `continue` та виняток, що розкручує стек. Для всіх
них рантайм проходить стеком і виконує кожен незавершений `finally` дорогою назовні.
`Environment.Exit`, `Environment.FailFast`, необроблений `StackOverflowException`,
fail-fast рантайму чи вбивство процесу операційною системою - це **не** розкрутка
стека: вони зносять процес там, де він стоїть, а незавершені `finally` просто
покидаються. Стеком ніхто не проходить, тож ніщо на ньому не виконується.

Хибне переконання: «`finally` виконується завжди, тож прибирання там у безпеці». Він
завжди виконується для *керованого потоку виконання*. `Environment.Exit` виглядає як
охайний виклик «зупини програму», але це не `return` - це негайне знесення процесу,
і кожен `finally` між ним і `Main` пропускається. Що особливо болить - це контраст:
хуки виходу з процесу на кшталт `AppDomain.ProcessExit` *таки* спрацьовують на
`Environment.Exit` (цей експонат використовує такий як свій аудитор), тож механізми,
яким ти довіряв найменше, виконуються, а `finally`, якому ти довіряв найбільше, - ні.

## ✅ Виправлення

Перерви через керований потік виконання - `return` чи throw - щоб стек справді
розкрутився і `finally` виконався.

```csharp
void RunBatch()
{
    try
    {
        // ... обробка записів ...
        return; // розкручується нормально - finally нижче все одно виконується
    }
    finally
    {
        FlushAuditLog(); // виконується на кожному керованому шляху виходу
    }
}
```

Повна версія в [Good.cs](Good.cs); помилка - у [Bad.cs](Bad.cs).

| Підхід | Коли він доречний |
|---|---|
| `return` / throw замість `Environment.Exit` | Ти глибоко в стеку викликів і хочеш спинитися - розкрути нормально, щоб кожен `finally` дорогою назовні виконався; постав код виходу раз, нагорі. |
| Скидай *перед* виходом | Тобі справді треба викликати `Environment.Exit` (шлях аварійного завершення CLI) - зроби довговічну роботу спершу, потім вийди, ніколи не після. |
| `AppDomain.ProcessExit` для прибирання в останню чергу | Прибирання мусить пережити навіть `Environment.Exit` - ProcessExit-хендлер на нього спрацьовує, але це best-effort, обмежений у часі й не спрацьовує на жорсткому краху. |
| Не роби `finally` єдиною копією | Стан важливий (гроші, аудит) - зроби операцію рестартовною чи транзакційною, щоб пропущений скид був відновлюваним, а не втраченим. |

## 😈 Ще гірший родич

`Environment.Exit` - це принаймні виклик, який ти написав і можеш згрепати. Тихі
родичі - ті, яких жоден рядок твого коду не називає. Необроблений
`StackOverflowException` неможливо зловити *і* він пропускає кожен `finally`, поки
рантайм робить fail-fast - глибока чи випадкова рекурсія стирає твоє прибирання без
винятку, який ти міг би зловити. `Environment.FailFast` (і власний fail-fast
рантайму на пошкодженні купи чи зламаному інваріанті) робить те саме за задумом, бо
сенс fail-fast саме в тому, щоб *не* виконувати більше керованого коду. А процес,
вбитий ОС, OOM-кілером чи втратою живлення, взагалі не отримує честі розкрутитися.
Кожен із них лишає твій «гарантований» `finally` невиконаним, і ті, що болять
найбільше, - саме ті, яких не видно в коді.

## 🎓 Поглиблений нюанс

- **`ProcessExit` не заміна `finally`.** Він спрацьовує на `Environment.Exit` і на
  нормальному завершенні, але обмежений у часі (рантайм лімітує, скільки хендлери
  можуть виконуватися), *не* спрацьовує на `FailFast` чи жорсткому краху, а виняток,
  кинутий усередині нього, ковтається. Це best-effort страховка, не гарантія.
- **`finally` виконується для *необробленого* винятку, але не завжди помітно.** Коли
  виняток необроблений, рантайм усе одно розкручує стек і виконує `finally` перед
  завершенням - тож звичайний `throw` безпечний для прибирання, на відміну від
  `FailFast`/`Exit`. Різниця - розкрутка (виконує `finally`) проти fail-fast (ні).
- **`finally`, що сам кидає чи виходить, - інший спосіб втратити прибирання.** Якщо
  тіло `finally` викликає `Environment.Exit` чи кидає (див.
  [0017-finally-that-lied](../0017-finally-that-lied/)), `finally`-блоки далі назовні
  теж пропускаються - той самий збій «стек перестав розкручуватися», на рівень вище.

## 🔎 Як знайти у своїй кодовій базі

- Грепни `Environment.Exit`, `Environment.FailFast` і `Process.Kill` усередині чи
  під `try`, що володіє `finally` - будь-яке прибирання, незавершене на цьому стеку,
  пропускається, коли виклик спрацьовує.
- Переглянь хелпери «fail fast» і «graceful shutdown»: якщо вони викликають
  `Environment.Exit`, поки запити, скиди чи транзакції в польоті, `finally`-блоки,
  покликані їх закрити, не виконуються.
- З боку симптомів: відсутні audit-записи, нескинуті логи чи незвільнені блокування,
  що корелюють із завершенням процесу на шляху *помилки*, тоді як щасливий шлях
  прибирає нормально; коди виходу, що кажуть «успіх» на прогонах, які лишили роботу
  напівзробленою.
- Клади довговічну, обов'язкову роботу (commit, скид, звільнення) перед викликом
  виходу або у рестартовній/транзакційній формі - ніколи винятково у `finally`, повз
  який знесення процесу може пройти.

# #0076 - Конструктор, що кидає, лишає ресурс витікати

## 💥 Симптом

Правило, якого вчить цей експонат: **щойно ти захопив ресурс, ти мусиш звільнити
його, перш ніж випустити виняток назовні - `throw` не зробить цього за тебе.**
Тут воно розігрується в конструкторі. Пул з'єднань (чи пул файлових дескрипторів,
чи семафор) вичерпується під навантаженням, і ніхто не може знайти витік. Кожен
`using` на місці, кожен `Dispose` виглядає правильним - а слоти йдуть і не
повертаються. Це стається лише на шляху помилки: конструктор захоплює свій слот,
потім натикається на поганий аргумент чи невдале з'єднання і кидає, *усе ще
тримаючи цей слот*, а `using`, в який ти його загорнув, не звільняє нічого.

## 🔍 Проблемний код

```csharp
using var conn = new PooledConnection(host); // 💥 ctor бере слот, потім кидає - conn так і не присвоєно

sealed class PooledConnection : IDisposable
{
    public PooledConnection(string host)
    {
        Pool.Take();                       // захоплюємо
        if (string.IsNullOrEmpty(host))    // потім валідуємо -> кидає, а слот уже взято
            throw new ArgumentException("host is required");
    }
    public void Dispose() => Pool.Return();
}
```

## 🧠 Що насправді відбувається

`using var x = new T(...)` звільняє `x` у кінці його області - але лише якщо `x`
взагалі було присвоєно. Коли конструктор кидає, вираз `new` ніколи не
завершується, тож змінна не присвоюється, і `using` (чи пізнішому `Dispose`)
нічого прибирати. Будь-який ресурс, що конструктор уже захопив до того, як кинув -
слот пулу, файловий дескриптор, блокування, нативний буфер - тепер утримується
об'єктом, якого не існує: посилання ніде немає, і жоден `Dispose` ніколи не
виконається. `using` захистив тебе від кожної помилки *після* конструювання і від
жодної *під час* нього.

Хибне переконання: «`using` гарантує `Dispose`, тож ресурс у безпеці». Він
гарантує `Dispose` лише для *успішно сконструйованого* об'єкта. Тієї миті, коли ти
захопив ресурс, звільнення - *твоя* відповідальність, поки ресурс не переданий
безпечно в `using` чи поле; а між захопленням і цією передачею `throw` проходить
повз нього напряму. Конструктор, що захоплює й потім робить щось, що може кинути -
валідує аргумент, відкриває сокет, читає конфіг - має саме таке вікно: ресурс
живий, об'єкт ще ні, і виняток у ньому тихо лишає ресурс витікати, тільки на шляху
помилки, який твої тести щасливого шляху ніколи не проходять.

## ✅ Виправлення

Зроби конструктор стійким до винятків: якщо щось після захоплення може кинути,
звільни взяте, перш ніж випустити виняток назовні.

```csharp
public PooledConnection(string host)
{
    Pool.Take();
    try
    {
        if (string.IsNullOrEmpty(host))
            throw new ArgumentException("host is required");
        // відкрити сокет, прочитати конфіг, будь-що інше, що може кинути
    }
    catch
    {
        Dispose();   // звільни слот, потім прокинь далі
        throw;
    }
}
```

Повна версія в [Good.cs](Good.cs); помилка - у [Bad.cs](Bad.cs).

| Підхід | Коли він доречний |
|---|---|
| `try { ... } catch { Dispose(); throw; }` у конструкторі | Конструктор мусить захопити, а потім зробити роботу, що кидає - огороди її, щоб будь-яка помилка звільнила взяте перед поширенням. |
| Захоплюй останнім / валідуй першим | Кинути може лише валідація - перевір аргументи *до* того, як береш ресурс, тоді виняток стається, коли нічого не захоплено. |
| Статичний фабричний метод | Винеси захоплення з конструктора - `Connection.Open(host)` захоплює і, у разі невдачі, звільняє й кидає; конструктор лише зберігає вже захоплений дескриптор. |
| Не володій ресурсом | Приймай ресурс як *параметр* конструктора (dependency injection) - його час життя належить викликачу, і виняток у твоєму ctor не лишає витікати нічого захопленого тобою. |

## 😈 Ще гірший родич

Слот пулу має бодай `Dispose`, до якого ти не дійшов; *некерований* ресурс,
захоплений у конструкторі, що кидає, не має жодної страховки. Якщо конструктор
виділяє нативний дескриптор (файл, сокет, `Marshal.AllocHGlobal`) і потім кидає,
звільнити його міг би лише фіналізатор - а об'єкт, чий конструктор кинув, **не
реєструється для фіналізації**, тож навіть фіналізатор ніколи не виконається.
Дескриптор витікає до завершення процесу. Варіант з ініціалізатором поля ховає
захоплення повністю: `private readonly Stream _s = File.OpenRead(path);`
виконується *перед* тілом конструктора, тож якщо пізніший ініціалізатор поля чи
тіло кине, `_s` відкритий, без посилань і незакритий - витік без жодного видимого
захоплення в конструкторі.

## 🎓 Поглиблений нюанс

- **Невдалий конструктор пригнічує фіналізацію.** Рантайм не викликає фіналізатор
  об'єкта, чий конструктор кинув - він не був повністю сконструйований - тож
  фіналізаторне прибирання, на яке покладаються як на страховку, тут не спрацьовує.
  Страховка - це `try/catch`-звільнення *усередині* конструктора.
- **`using` прив'язує `Dispose` до *змінної*, не до `new`.** Витік саме в тому, що
  змінну не присвоєно. Винесення захоплення (фабрика, що повертає вже збудований
  об'єкт з ресурсом) відновлює гарантію: `using` викликача тоді огортає повністю
  сконструйований об'єкт.
- **Ініціалізатори об'єкта продовжують вікно за межі конструктора.** `new
  Conn(host) { Timeout = Compute() }` виконує `Compute()` *після* повернення
  конструктора, але *до* присвоєння змінної - якщо воно кине, успішно збудований
  `Conn` витікає, бо `using` / присвоєння не сталося. Безпечний об'єкт збудували й
  викинули на підлогу.

## 🔎 Як знайти у своїй кодовій базі

- Грепни конструктори, що захоплюють (`Open`, `Connect`, `Rent`, `Acquire`, `new
  SemaphoreSlim`, `AllocHGlobal`, `File.Open*`) і потім роблять щось, що може
  кинути - валідацію, ще одне захоплення, I/O - без `try/catch`, що звільняє.
- Дивись на `IDisposable`-типи зі справжньою роботою в конструкторі та на
  ініціалізатори полів, що відкривають ресурси (`= File.OpenRead(...)`, `= new
  HttpClient()`), у типі, чиє конструювання може десь впасти.
- З боку симптомів: витоки пулу / дескрипторів / семафора, що ростуть лише під
  навантаженням помилок; лічильник ресурсу, що дрейфує вгору саме в тих запусках,
  де входи були невалідні; витоки, що зникають, коли прибрати проблемний вхід.
- Обирай захоплення через фабрику (чи прийом ресурсу параметром), а не захоплення
  всередині конструктора, що може кинути; коли мусиш захопити там, огортай роботу
  після захоплення в `try { ... } catch { Dispose(); throw; }`.

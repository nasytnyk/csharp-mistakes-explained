# #0085 - Type-pattern пропускає null

## 💥 Симптом

`switch`, що «обробляє кожен тип, який може прийти», тихо неправильно обробляє рівно
один вхід: `null`. Рядки рендеряться, числа рендеряться, а потім рядок із відсутнім
опціональним полем або валить роботу, або експортує маркер чужого типу там, де мала
бути порожня клітинка. Гілка `string` ось вона - але відсутнє значення до неї так і не
дійшло.

## 🔍 Проблемний код

```csharp
string Format(object? value) => value switch
{
    string s => s,
    int n    => n.ToString(),
    _        => "<unsupported>", // 💥 null не матчить жоден type-pattern і потрапляє сюди
};
```

## 🧠 Що насправді відбувається

Type-pattern - `string s`, `case string:`, `is int n` - перевіряє, чи значення *є
екземпляром* того типу, а `null` не є екземпляром жодного типу. `null is string` це
`false`, `null is object` теж `false`; рантайм-перевірка типу, яку робить кожен
type-pattern, просто не може зматчити значення, за яким немає жодного об'єкта. Тож
null-значення провалює кожну типізовану гілку switch і провалюється у discard-гілку
`_`, яку писали зі значенням «якийсь тип, що я не передбачив», - а не «значення
відсутнє».

Хибне переконання - «`string s` обробляє рядки, а null-рядок це досі рядок». На рівні
системи типів змінна `string?` може тримати null, але pattern match - це рантайм-
перевірка екземпляра, а в рантаймі null це відсутність екземпляра, не рядок без
символів. Далі default-гілка робить те, що має робити «неочікуваний тип», - кидає,
логує помилку, видає плейсхолдер, відхиляє запис - і застосовує це до того, що
насправді є звичайним порожнім полем. Компілятор не попереджає, бо switch *таки*
вичерпний: `_` ловить null, просто не в ту гілку.

## ✅ Виправлення

Матч `null` явно константним патерном `null`, і постав його перед типізованими
гілками, щоб відсутній випадок класифікувався навмисне.

```csharp
string Format(object? value) => value switch
{
    null     => "",           // відсутнє поле рендериться порожнім
    string s => s,
    int n    => n.ToString(),
    _        => "<unsupported>",
};
```

Повна версія в [Good.cs](Good.cs); помилка - у [Bad.cs](Bad.cs).

| Підхід | Коли він доречний |
|---|---|
| Гілка `null` | Прямий фікс - `null => ...` (константний патерн, єдине, що матчить null) дає відсутньому значенню власний визначений результат замість default. |
| `null or string s` | Null має поводитися як випадок рядка - об'єднай їх, напр. `null or "" => "empty"`, щоб відсутнє й порожнє мали одну гілку навмисне. |
| Гард на межі | Значення тут не має бути null - відхили чи задефолть його там, де воно входить (обов'язкова колонка, `?? ""`), щоб switch бачив лише реальні екземпляри. |
| Лишай `_` для справжніх невідомих | Тримай discard-гілку зі значенням «справді неочікуваний тип» - щойно `null` має власну гілку, влучання в `_` це реальний сигнал (залогуй, алерт), а не null у масці. |

## 😈 Ще гірший родич

Тут `null` принаймні потрапляє у видиму default-гілку; тихіший родич - *позиційний* чи
*властивісний* патерн, що так само мовчки відкидає null і не має default, щоб його
зловити. `case Person("Ada", _):` не матчить null-`Person` - деконструкція не може
виконатися на null - і `case { Age: > 18 }:` теж не матчить null-посилання, бо немає
об'єкта, з якого прочитати `.Age`. У `switch`-стейтменті без `default` null просто
випадає знизу й не виконує нічого, тож блок «обробити цю форму» тихо пропускається саме
для входу, що найімовірніше є багом. І дзеркальна пастка: `case string { Length: > 0 }`
пропускає і null, *і* порожній рядок, тож два різні «немає реального тексту» входи беруть
провал з двох різних причин.

## 🎓 Поглиблений нюанс

- **`null` - єдиний патерн, що матчить null.** Константний патерн `null` (і `not null`) -
  єдиний спосіб перевірити на нього; кожен type-pattern, позиційний і властивісний патерн
  робить рантайм-перевірку екземпляра, яку null провалює. `var x` теж «матчить» null - але
  лише тому, що `var` матчить усе й не робить перевірки типу взагалі.
- **Switch із `_` вичерпний, тож попередження не спрацьовує.** Перевірка вичерпності
  компілятора задоволена тієї ж миті, коли є `_` - він не знає, що ти мав на увазі `_` для
  чужих типів, а не для null. Прибери `_`, і компілятор помітить пропущену обробку null
  (CS8509) - привід віддавати перевагу явним гілкам над catch-all, де важлива коректність.
- **`Nullable<T>` value-типи матчать свою базову гілку, не null-гілку.** `int?` із null
  усе одно провалює `case int n` (немає boxed-значення), тоді як `int?` із `5` матчить
  `case int n` з `n == 5` - тож те саме правило «пропускає null» діє, і null-`int?` теж
  потребує власної гілки `null`.

## 🔎 Як знайти у своїй кодовій базі

- Грепни `switch`-вирази й стейтменти над `object`, `object?` чи nullable-reference входами,
  чиї гілки - усі type/property/positional патерни з `_` (чи без) default - спитай, що
  робить null-вхід і чи це відповідає наміру.
- Дивись на форматери, серіалізатори, маппери й диспетчери, що живляться з data reader-ів,
  десеріалізаторів чи рефлексії, де відсутнє поле приходить як null і має означати
  «порожнє», не «невідомий тип».
- З боку симптомів: плейсхолдер чи маркер помилки в виводі для записів із відсутнім
  опціональним полем, експорти, що падають на першому null, логи «unsupported type», чиє
  значення насправді просто відсутнє.
- Додай явну гілку `null` (чи `null or ...`), тримай `_` для справді неочікуваних типів,
  або прибери `_`, щоб компілятор змусив тебе вирішити, що робить null.

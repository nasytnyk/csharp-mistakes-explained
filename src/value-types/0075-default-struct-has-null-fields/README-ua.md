# #0075 - default-структура має null-поля

## 💥 Симптом

`NullReferenceException` вилітає зі значення, яке система типів клянеться повністю сконструйованим -
структури, чий конструктор «завжди» створює свій список, а `.Items` при цьому null. Падіння - на
першому ж `.Add`, далеко від місця, де структуру створили, і сама структура не null (value type ним
бути не може) - null лише її поля.

## 🔍 Проблемний код

```csharp
struct Cart { public List<string> Items; public Cart() => Items = new(); }

var carts = new Cart[100];    // 💥 елементи масиву - default(Cart): конструктор не виконався
carts[0].Items.Add("SKU-1");  // Items дорівнює null -> NullReferenceException
```

## 🧠 Що насправді відбувається

`default(T)` та виділення масиву створюють значення шляхом **обнулення пам'яті** - вони не запускають
ані конструктора, ані ініціалізаторів полів. Для структури кожне поле стає своїм нулем: числові - `0`,
`bool` - `false`, а кожне **reference**-поле (`List<T>`, `string`, вкладений клас) - `null`.
`new Cart()` запускає безпараметровий конструктор і ініціалізує `Items`; `new Cart[n]` і
`default(Cart)` - ні: вони віддають `Cart`, який *виглядає* сконструйованим (справжнє значення, не
null), але ніколи не виконав код, що заповнює його поля.

Хибне переконання: «конструктор гарантує, що `Items` встановлено». Він гарантує це лише для
`new Cart()`. Структуру можна створити *без* її конструктора - `default`, `new T[n]`, непризначене
поле структурного типу, `out`-параметр - і кожен такий шлях іде просто в обнулену пам'ять. Тип
non-nullable і виглядає повністю збудованим; null - на рівень нижче, де ніщо не змусило тебе глянути.

## ✅ Виправлення

Сконструюй кожен елемент - не покладайся на конструктор структури для `default` / масивних шляхів:

```csharp
var carts = new Cart[100];
for (int i = 0; i < carts.Length; i++)
    carts[i] = new Cart(); // запусти конструктор на кожен слот, щоб Items був справжнім списком
```

Повна версія в [Good.cs](Good.cs); помилка - у [Bad.cs](Bad.cs).

| Підхід | Коли він доречний |
|---|---|
| Конструювати кожен елемент (`arr[i] = new Cart()`) | Треба масив структур з ініціалізованими полями - заповни явно, бо `new T[n]` ніколи не запускає твій конструктор. |
| Зробити це `class` | Тип володіє reference-станом, який мусить існувати - масив класу це `[null]`, чесний сигнал, що треба `new` кожен елемент, і ти не отримаєш напівзбудований екземпляр із `default`. |
| Лінивий / гарантований доступ | Віддавай список через властивість, що ініціалізує при першому доступі (`Items ??= new()`), тож навіть `default`-значення поверне справжній список. |
| Значення без reference-полів | Якщо воно мале й справді value-like, взагалі уникай мутабельних reference-полів - тоді `default` уже є повним, валідним значенням. |

## 😈 Ще гірший родич

`NullReferenceException` - *гучна* половина цього бага. Його тихий близнюк - поле, що повертається
неправильним значенням замість null: `struct` із `public decimal Rate = 1.0m;` (чи
`public bool Enabled = true;`), ініціалізований у коді й матеріалізований через `default` чи масив,
повертається як `Rate = 0` і `Enabled = false` - без падіння, лише множник, що тихо обнуляє кожен
підсумок, і фіча, що тихо вимикається, тільки на шляху, що використав масив. Той самий корінь -
`default` пропускає конструювання - протилежна сходинка страху: reference-поле кидає там, де видно,
value-поле відправляє неправильне число там, де ні. Те, що падає, - це те, з чим тобі пощастило.

## 🎓 Поглиблений нюанс

- **Структура з ініціалізаторами полів не скомпілюється без оголошеного конструктора.**
  `struct Cart { public List<string> Items = new(); }` - помилка C#, якщо не написати ще й
  конструктор - і навіть тоді ініціалізатор працює лише на `new Cart()`, ніколи на `default` /
  масиві. Мова змушує тебе написати конструктор; вона не може змусити кожен шлях створення його
  викликати.
- **`default` неминучий для value type.** Можна відрадити зловживання, але не можна зупинити
  `default(Cart)`, `new Cart[n]`, ріст `List<Cart>` чи непризначене поле `Cart` - рантайм роздає
  нуль-значення для всіх них. Кожна BCL-структура така сама: `default(Guid)` це `Guid.Empty`,
  `default(DateTime)` це `0001-01-01` (див. [0054-new-guid-is-empty](../0054-new-guid-is-empty/)) -
  `default` це нуль-значення, ніколи не null і не «не задано». Якщо структура не виживає повністю
  обнуленою, це має бути клас.
- **`out`-параметри й узагальнений `default(T)` теж це чіпляють.** `Dictionary.TryGetValue` ставить
  структурний `out` у `default` при промаху; узагальнений метод, що повертає `default(T)`, повертає
  обнулену структуру - обидва дають тобі значення з null-полями без жодного видимого `new`.

## 🔎 Як знайти у своїй кодовій базі

- Грепни `struct`-типи з reference-полями (`List<>`, `string`, масиви, клас) і конструктором, що їх
  ініціалізує - тоді шукай `new ThatStruct[`, `default(ThatStruct)` та `TryGetValue` / `out`-вжитки,
  що пропускають конструктор.
- З боку симптомів: `NullReferenceException` на полі структурного значення, яке «не може бути null»;
  падіння на першому вжитому елементі масиву, першому промаху `TryGetValue` чи першому непризначеному
  полі структурного типу.
- Для value-like даних, що мусять володіти колекцією, обирай `class`, або віддавай колекцію через
  властивість, що ініціалізує ліниво, щоб `default` усе одно працював.
- Якщо це мусить лишатись структурою, заповнюй масиви явно (`arr[i] = new(...)`) і ніколи не
  припускай, що `default`-екземпляр запустив твій конструктор.

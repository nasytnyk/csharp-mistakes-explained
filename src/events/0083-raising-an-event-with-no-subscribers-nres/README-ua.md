# #0083 - Підняти подію без підписників

## 💥 Симптом

Фіча працювала на кожній машині, де її тестували, а потім кинула
`NullReferenceException` у проді - зсередини видавця, на рядку, що просто піднімає
подію. Ніщо не було null в очевидному сенсі: сервіс існує, замовлення валідне, подія
оголошена. Бракує єдиного - *підписника*, і на шляху, що виконався, ніхто не приєднав
обробник.

## 🔍 Проблемний код

```csharp
public event EventHandler<string>? OrderPlaced;

public void PlaceOrder(string id, decimal amount)
{
    // ... зберегти замовлення ...
    OrderPlaced(this, id); // 💥 немає обробників -> OrderPlaced це null -> NullReferenceException
}
```

## 🧠 Що насправді відбувається

Подія стоїть на полі multicast-делегата, і це поле - `null`, поки не станеться перший
`+=`. Підняти подію - це насправді *викликати делегат*, а виклик `null`-делегата - це
розіменування null: `OrderPlaced(this, id)` на порожній події це `null.Invoke(...)`.
Кожен `+=` ставить полю ненульовий об'єднаний делегат, а кожен `-=` може повернути його
до `null`, тож «чи кине це?» цілком залежить від того, чи хтось наразі підписаний -
стан, який видавець не контролює й зазвичай не бачить.

Хибне переконання - «подія оголошена, тож піднімати її безпечно». Оголошення події
лише створює слот; воно не кладе туди обробник. Причина, чому це переживає тести,
жорстока: тести майже завжди приєднують обробник (бо саме так вони спостерігають
подію), тож делегат ненульовий і підняття працює - рівно та умова, що ховає баг. Прод
потім виконує шлях, де підписника ще не під'єднали, прибрали, чи він належить
вимкненому компоненту, - і той самий рядок, що пройшов кожен тест, розіменовує null.
Компілятор навіть попереджає (`CS8602`, «розіменування можливо-null-посилання») на
nullable-події, і саме це попередження люди відмахують.

## ✅ Виправлення

Піднімай подію null-умовним оператором, щоб порожній список викликів був no-op, а не
крахом.

```csharp
public void PlaceOrder(string id, decimal amount)
{
    // ... зберегти замовлення ...
    OrderPlaced?.Invoke(this, id); // немає підписників -> no-op
}
```

Повна версія в [Good.cs](Good.cs); помилка - у [Bad.cs](Bad.cs).

| Підхід | Коли він доречний |
|---|---|
| `E?.Invoke(args)` | Стандартне підняття - null-умовний виклик це ідіома для кожної події, і він потокобезпечний, якщо обробник відпишеться між перевіркою на null і викликом. |
| Захищений метод `OnX` | Клас, від якого інші успадковуються - загорни підняття у `protected virtual void OnOrderPlaced(...)`, що робить `?.Invoke`, тож кожне місце виклику й підклас піднімають безпечно. |
| Засій подію порожнім обробником | Хочеш, щоб поле ніколи не було null - `public event EventHandler<string> OrderPlaced = delegate { };` робить голе `OrderPlaced(this, id)` безпечним ціною одного завжди присутнього no-op-підписника. |
| Пара «скопіюй, тоді виклич» | Стиль до-`?.` чи доданий null-чек - спершу скопіюй делегат у локальну (`var h = OrderPlaced; if (h != null) h(...)`), щоб уникнути гонки, де `-=` занулює його посеред перевірки; `?.Invoke` робить це за тебе. |

## 😈 Ще гірший родич

Краш тієї ж миті, коли підписників немає, - гучний і миттєвий: знаходиш швидко. Тихіший
родич - копіювання-з-перевіркою, написане *неправильно*: `if (OrderPlaced != null)
OrderPlaced(this, id)` повертає гонку - обробник може відписатися в іншому потоці між
перевіркою й викликом, і підняття все одно кине NRE, але тепер лише подеколи, лише під
навантаженням і ніколи в дебагері. Ще гидкіший - зворотний збій, від якого null-умовний
не рятує: щойно підписник таки з'явиться, multicast-подія викликає обробники по черзі,
і якщо один кине, обробники після нього не виконаються (див.
[0052-one-handler-kills-the-rest](../0052-one-handler-kills-the-rest/)) - тож «зробити
підняття безпечним» це лише половина контракту; виклик *чужих* обробників - інша.

## 🎓 Поглиблений нюанс

- **`?.Invoke` читає поле раз.** Null-умовний оператор обчислює `OrderPlaced` один раз
  у прихований тимчасовий, тоді перевіряє на null і викликає цю копію - рівно той
  потокобезпечний патерн «скопіюй, тоді виклич», який раніше писали руками, тепер
  вбудований.
- **Nullable-анотація - це підказка.** Подія на полі має тип `EventHandler?`, бо
  стартує з null; попередження `CS8602` на `OrderPlaced(this, id)` - це компілятор, що
  тицяє прямо в цей баг. Сприймай його як задачу, не шум.
- **`event` обмежує викликачів, не тип-декларатор.** Зовнішній код може лише `+=`/`-=`;
  тип, що оголошує подію, - єдиний, хто може її викликати, - тож фікс живе на місці
  підняття, і на кожну подію є рівно одне місце, де це зробити правильно.

## 🔎 Як знайти у своїй кодовій базі

- Грепни підняття подій, написані як звичайний виклик - `SomeEvent(this, ...)` чи
  `SomeEvent(...)` - замість `SomeEvent?.Invoke(...)`; кожне кидає, щойно його список
  викликів порожній.
- Довіряй компілятору: `CS8602` на виклику події - це той баг; не глуши його через `!` -
  виправ через `?.Invoke`.
- З боку симптомів: `NullReferenceException`, що походить *зсередини* видавця на рядку
  підняття, краші лише коли фіча/модуль вимкнені чи під час старту до приєднання
  підписників, і код, що проходить тести (які підписуються), але падає в середовищах, де
  не підписуються.
- Стандартизуй `E?.Invoke(...)` (чи обгортку `protected virtual OnX`) для кожного
  підняття події, щоб «немає підписників» завжди було тихим no-op.

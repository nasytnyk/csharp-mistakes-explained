# #0080 - Масив з env потребує індексованих ключів

## 💥 Симптом

Allowlist ось він, у середовищі -
`ALLOWEDHOSTS=payments.acme.com,billing.acme.com,mail.acme.com`, три хости, через
кому, як хоче кожен інший інструмент. Застосунок біндить його в `string[]` - і масив
повертається **порожнім**. Ні помилки, ні попередження - просто нуль елементів там,
де налаштовано три, і те, що порожній список означає далі (блокувати все чи дозволити
все), тепер тихо керує продакшеном.

## 🔍 Проблемний код

```csharp
// ALLOWEDHOSTS=payments.acme.com,billing.acme.com,mail.acme.com
var config = new ConfigurationBuilder().AddEnvironmentVariables().Build();

string[] allowed = config.GetSection("AllowedHosts").Get<string[]>() ?? []; // 💥 порожньо
```

## 🧠 Що насправді відбувається

У конфігурації немає поняття списку через кому. Масив зберігається як окремі ключі з
числовими індексами - `AllowedHosts:0`, `AllowedHosts:1`, `AllowedHosts:2` - і
масив-біндер відновлює `string[]`, читаючи ці індексовані дочірні. Одна змінна
середовища на ім'я `ALLOWEDHOSTS` створює один ключ, `AllowedHosts`, чиє *значення* -
увесь рядок `"payments.acme.com,billing.acme.com,mail.acme.com"`. Той ключ має
скалярне значення й **жодних індексованих дочірніх**, тож `Get<string[]>()` не
знаходить чого біндити й повертає null; `?? []` перетворює це на порожній масив. Кома -
просто символ усередині одного рядка, біндер ніколи не трактує її як роздільник.

Хибне переконання: «список у env-змінній - через кому, як `PATH`». Кожне налаштування
у формі масиву, що читає система конфігурації .NET, приходить із *кількох ключів*, по
одному на елемент. Для змінних середовища роздільник ієрархії `:` пишеться як `__`, тож
масив живе в `ALLOWEDHOSTS__0`, `ALLOWEDHOSTS__1`, `ALLOWEDHOSTS__2` - три змінні, не
одна. Втисни весь список в одну змінну - і біндер бачить скаляр, віддає тобі нічого, а
збій тихий, бо «немає індексованих дочірніх» - це не помилка, а просто порожній
результат.

## ✅ Виправлення

Дай кожному елементу власний індексований ключ. Для змінних середовища це означає одну
змінну на запис, із суфіксом `__0`, `__1`, `__2`.

```bash
ALLOWEDHOSTS__0=payments.acme.com
ALLOWEDHOSTS__1=billing.acme.com
ALLOWEDHOSTS__2=mail.acme.com
```

```csharp
string[] allowed = config.GetSection("AllowedHosts").Get<string[]>() ?? [];
// -> ["payments.acme.com", "billing.acme.com", "mail.acme.com"]
```

Повна версія в [Good.cs](Good.cs); помилка - у [Bad.cs](Bad.cs).

| Підхід | Коли він доречний |
|---|---|
| Індексовані env-ключі (`KEY__0`, `KEY__1`, ...) | Канонічне представлення - кожен елемент це власний ключ, і воно однаково проходить через кожен провайдер (JSON-масив, env, командний рядок). |
| JSON-масив в appsettings | Значення живуть у файлі, а не в середовищі - `"AllowedHosts": ["a", "b"]` біндиться в `string[]` напряму, без ручних індексів. |
| Розбий скаляр сам, свідомо | Ти справді хочеш одну змінну через кому - прочитай її як `string` і `value.Split(',')` явно, щоб парсинг був видимим і навмисним, а не припущеним. |
| Валідуй кількість на старті | Будь-який масив-із-конфігу - перевіряй непорожній (чи очікуваного розміру) результат на буті, щоб криво задана змінна падала гучно, а не біндилась у `[]`. |

## 😈 Ще гірший родич

Тут порожній allowlist принаймні *консервативний* - якщо код читає «порожнє означає не
дозволяти нічого», ти отримаєш гучний простій, а не пробій. Небезпечне дзеркало - код,
що читає порожній allowlist як «обмежень не задано, дозволити все»: той самий тихий збій
біндингу тепер відкриває кожен вихідний хост замість закрити їх, а контроль безпеки, який
ти вважав задеплоєним, узагалі не завантажився. І частковий варіант кусає: задай
`ALLOWEDHOSTS__0` і `ALLOWEDHOSTS__2`, але пропусти `__1` - і біндер спиняється на першій
дірі, тихо обрізаючи масив до одного елемента; список не порожній, тож перевірка за
кількістю проходить, а двох із трьох хостів немає.

## 🎓 Поглиблений нюанс

- **`__` - env-написання `:`.** Імена змінних середовища не можуть містити `:` у деяких
  шелах, тож провайдер мапить подвійне підкреслення на роздільник ієрархії.
  `ALLOWEDHOSTS__0` стає конфіг-ключем `AllowedHosts:0`; одинарне підкреслення не робить
  нічого особливого.
- **Індекси мають бути суцільними від 0.** Масив-біндер читає `:0`, `:1`, `:2` до першого
  відсутнього індексу, тоді спиняється - діра тихо обрізає масив, а не пропускає дірку,
  тож `:0` + `:2` дає одноелементний масив.
- **JSON-масиви розкладаються в ті самі індексовані ключі.** `"AllowedHosts": ["a","b"]`
  в appsettings зберігається всередині як `AllowedHosts:0=a`, `AllowedHosts:1=b` - саме
  тому env-оверрайд `AllowedHosts__1` заміняє другий елемент на місці, а не весь масив.

## 🔎 Як знайти у своїй кодовій базі

- Грепни `.Get<string[]>()`, `.Get<List<` і властивості-масиви/колекції, що біндяться з
  конфігурації, тоді перевір, як відповідне значення задане в середовищі - одна змінна
  через кому це той баг.
- Переглянь деплой-поверхні (Kubernetes, Compose, CI-змінні) на env-записи, що пакують
  список в одне значення через кому чи крапку з комою там, де код очікує масив.
- З боку симптомів: налаштування-масив, що біндиться в порожнє (чи в один елемент) без
  помилки, allowlist/списки отримувачів/списки ендпоінтів, тихо порожні на одному
  середовищі, і конфіг, що працює з `appsettings.json` (справжнього JSON-масиву), але не
  з його env-оверрайду.
- Обирай індексовані ключі чи JSON-масив; якщо роздільникового скаляра не уникнути, розбий
  його явно в коді й валідуй отриману кількість на старті.

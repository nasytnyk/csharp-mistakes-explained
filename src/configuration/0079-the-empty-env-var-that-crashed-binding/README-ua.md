# #0079 - Порожня env-змінна, що зламала біндинг

## 💥 Симптом

Застосунок працює всюди - на твоїй машині, в CI, на staging - і валиться на єдиному
деплої, де змінну середовища виставили в порожнє значення. Старт кидає
`InvalidOperationException: Failed to convert configuration value at
'Worker:Retries' to type 'System.Int32'`, хоча числа ніхто не чіпав. `appsettings.json`
досі каже `5`. Env-змінна «порожня», що *відчувається* як «не задана» - але для
конфігурації це реальне значення `""`, а `""` - не `int`.

## 🔍 Проблемний код

```csharp
// дефолт з appsettings - 5; деплой виставляє WORKER__Retries у порожнє значення
var config = new ConfigurationBuilder()
    .AddInMemoryCollection(new() { ["Worker:Retries"] = "5" })
    .AddEnvironmentVariables()
    .Build();

int retries = config.GetValue<int>("Worker:Retries"); // 💥 конвертація "" в int кидає
```

## 🧠 Що насправді відбувається

Конфігурація - це плоска мапа строкових ключів на строкові значення, нашарована за
провайдерами, і **перемагає останній**. Змінна середовища, що існує, але містить
порожній рядок, - це присутній ключ зі значенням `""`, тож провайдер env-змінних, що
стоїть над твоїми JSON-дефолтами, перекриває `Worker:Retries = "5"` на
`Worker:Retries = ""`. Немає поняття «порожнє означає провалитися на шар нижче»:
присутнє є присутнім. Далі `GetValue<int>` (як і `Bind`, і біндинг options)
намагається конвертувати це `""` в `Int32`, не може, і кидає
`InvalidOperationException` на старті.

Хибне переконання: «якщо я не дам env-змінній реального значення, використається мій
дефолт з `appsettings.json`». Виставити змінну в порожнє - це не те саме, що лишити її
незаданою. `export WORKER__Retries=` у шелі, порожнє значення в Kubernetes-маніфесті,
CI-змінна, оголошена, але не заповнена - усі створюють присутній, порожній оверрайд, що
затіняє твій дефолт і потім вибухає, щойно значення прочитають як щось інше, ніж рядок.
Це проблема *форми конфігу* в масці кодового стек-трейсу - тому розслідування
починається не там.

## ✅ Виправлення

Трактуй порожнє значення як «не задано»: прочитай сирий рядок, відкотись до дефолту,
якщо він порожній чи з пробілів, і парси лише реальний текст.

```csharp
var raw = config["Worker:Retries"];
int retries = string.IsNullOrWhiteSpace(raw) ? DefaultRetries : int.Parse(raw);
```

Повна версія в [Good.cs](Good.cs); помилка - у [Bad.cs](Bad.cs).

| Підхід | Коли він доречний |
|---|---|
| Перевірити сирий рядок на blank, тоді парсити | Одне значення зі здоровим дефолтом - `IsNullOrWhiteSpace(raw) ? fallback : Parse(raw)` перетворює порожній оверрайд назад на «не задано». |
| Options + `Validate` з чітким повідомленням | Цілий options-об'єкт - валідуй при біндингу, щоб погане/порожнє значення падало з «Worker:Retries має бути додатним цілим», а не з невиразною помилкою конвертера. |
| `ValidateOnStart()` (fail fast, свідомо) | Ти *хочеш*, щоб поганий конфіг спиняв застосунок - але з повідомленням, що називає налаштування, навмисне, а не зі стек-трейсом конвертера в глибині запиту. |
| Лагодь деплой, а не лише код | Blank прийшов із CI/маніфесту - прибери змінну (або дай реальне значення), щоб вона перестала затіняти дефолт; потрібні і загартування коду, і гігієна конфігу. |

## 😈 Ще гірший родич

Краш на старті - це *щасливий* результат: він гучний, миттєвий і не дає поганому
конфігу нічого зробити. Тихий родич - той самий порожній оверрайд, що біндиться в тип,
де `""` цілком валідне значення. Порожній `WORKER__Retries`, прив'язаний до `string`,
дає тобі `""`, а не твій дефолт - і тепер якийсь `int.Parse` нижче падає в глибині
запиту, або порожній connection string вказує в нікуди, або порожній рядок feature-flag
трактується як «вимкнено». Ще гірше - порожній оверрайд на значенні, що *приводиться*
тихо: порожній рядок, прив'язаний там, де код робить `raw ?? "default"`, бачить `""` (не
null), лишає порожнє й прослизає повз null-coalescing-гард, який ти вважав захистом.
Версія, що кидає на старті, - та, яку можна знайти; ті, що проливають порожній рядок у
бізнес-логіку, - ті, що піднімають тебе о 3-й ночі.

## 🎓 Поглиблений нюанс

- **Порожнє - не відсутнє, а відсутнє - не порожнє.** Відсутній ключ повертає
  `default(T)` з `GetValue<int>` (тихий `0`); присутній-але-порожній ключ повертає `""`
  і *кидає* при конвертації. Той самий намір «я цього не задавав» - два протилежні
  режими збою, один тихий, один гучний.
- **`__` - роздільник вкладеності для env-змінних.** `WORKER__Retries` мапиться на
  `Worker:Retries`, бо провайдер env-змінних перекладає подвійне підкреслення на
  роздільник ієрархії `:` (двокрапки недопустимі в іменах env у деяких шелах). Порожнє
  значення перекриває вкладений ключ так само, як це зробило б JSON-значення.
- **Порядок провайдерів вирішує, хто переможе.** `AddEnvironmentVariables()` після
  `AddJsonFile(...)` означає, що env-змінні перекривають JSON - зокрема порожні.
  Поміняй порядок - і blank програв би; але стандартний host builder навмисне ставить
  env-змінні останніми, тож у реальному застосунку порожній оверрайд перемагає.

## 🔎 Як знайти у своїй кодовій базі

- Грепни `GetValue<`, `.Get<` і `.Bind(` над налаштуваннями, що приходять із
  середовища, і спитай, що станеться, якщо ту змінну виставлено присутньою, але
  порожньою - якщо відповідь «конвертер кидає», це той баг.
- Переглянь деплой-поверхні: визначення CI/CD-змінних, env-блоки Kubernetes/Compose і
  шел-профілі, де `VAR=` (без нічого після `=`) ставить реальне порожнє значення, а не
  лишає незаданим.
- З боку симптомів: старт-`InvalidOperationException: Failed to convert configuration
  value at '...'` рівно на одному середовищі, тоді як JSON-дефолт видимо коректний;
  конфіг, що «працює локально», але вмирає в пайплайні, який підставив blank.
- Нормалізуй blank до «не задано» на межі читання (або валідуй options на старті з
  іменованими повідомленнями), і не дай деплой-конфігам оголошувати змінні, які вони
  насправді не заповнюють.

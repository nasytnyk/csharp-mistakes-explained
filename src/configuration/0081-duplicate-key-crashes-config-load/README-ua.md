# #0081 - Дубльований ключ валить завантаження конфігу

## 💥 Симптом

Сервіс не стартує на одному деплої. Старт кидає `InvalidDataException: Failed to
load configuration from file '.../appsettings.json'`, і перший інстинкт - проблема
зі шляхом чи правами: повідомлення вказує прямо на файл. Файл нормальний. Десь
усередині нього merge (чи вставлений блок) лишив той самий ключ визначеним двічі, а
JSON-провайдер конфігурації взагалі відмовляється завантажувати файл із дубльованим
ключем.

## 🔍 Проблемний код

```jsonc
{
  "Database": {
    "MaxConnections": 10,
    "CommandTimeout": 30,
    "MaxConnections": 100   // 💥 той самий ключ знову - увесь файл не завантажується
  }
}
```

```csharp
var config = new ConfigurationBuilder()
    .AddJsonFile("appsettings.json")
    .Build(); // кидає InvalidDataException тут
```

## 🧠 Що насправді відбувається

JSON-провайдер конфігурації розкладає документ у словник шляхів `Section:Key`, а
словник не може містити той самий ключ двічі. Коли він обходить об'єкт і доходить до
`MaxConnections` вдруге, він не перезаписує й не лишає останнє значення - він кидає
`FormatException: A duplicate key 'Database:MaxConnections' was found`, який провайдер
загортає в `InvalidDataException: Failed to load configuration from file '...'` і
пускає назовні з `Build()`. Увесь файл відхилено; жоден ключ із нього не завантажився.

Хибне переконання йде від самого JSON: специфікація JSON дозволяє дубльовані члени
об'єкта, і більшість парсерів тихо лишають останній, тож «дубльований ключ = останній
переможе» - розумна звичка з JavaScript, API й лог-тулінгу. Провайдер конфігурації .NET
навмисне так не робить - неоднозначний ключ трактується як пошкоджений файл, а не
розв'язний. І виняток, який ти справді бачиш, називає *файл*, тоді як корисна деталь
(який саме ключ) на рівень нижче, в `InnerException` - тож розслідування починається з
«чи правильний шлях?», а не «який ключ подвоєно?».

## ✅ Виправлення

Розв'яжи дублювання, щоб кожен ключ з'являвся рівно раз - зазвичай це merge-конфлікт
чи вставлений блок, який треба почистити.

```jsonc
{
  "Database": {
    "MaxConnections": 100,
    "CommandTimeout": 30
  }
}
```

Повна версія в [Good.cs](Good.cs); помилка - у [Bad.cs](Bad.cs).

| Підхід | Коли він доречний |
|---|---|
| Тримай кожен ключ раз | Прямий фікс - виріши, яке значення правильне, і видали інше; дублікат - ніколи не те, що ти мав на думці. |
| Читай `InnerException` заради ключа | Діагностика краху - верхнє повідомлення називає файл, але `InnerException` каже `A duplicate key '...' was found`; залогуй чи розгорни його, щоб одразу стрибнути на рядок. |
| JSON-схема / лінт у CI | Профілактика - валідатор чи лінт «без дубльованих ключів» на `appsettings*.json` ловить merge-артефакт до деплою. |
| Винеси env-специфічні оверрайди в окремий файл | Дублікат прийшов зі складання base + environment в одному файлі - клади оверрайд у `appsettings.{Environment}.json`, де повторений ключ легітимно *заміняє* між файлами, а не колізить усередині одного. |

## 😈 Ще гірший родич

Жорсткий краш на старті - це тут *хороший* результат: він гучний, миттєвий і не дає
конфігу, який ти не можеш осмислити, працювати. Гидкіший випадок - дублікат, що *не*
колізить усередині одного файлу: визнач `MaxConnections` в `appsettings.json` і знову
в `appsettings.Production.json` - і конфігурація зробить рівно те, для чого створена:
пізніший провайдер переможе, тихо. Це коректно й навмисне, але означає, що значення,
яке ти вважав заданим у базовому файлі, тихо перекрите environment-файлом, про який ти
забув, без жодної помилки, що вказала б туди (див.
[0070-env-var-overrides-appsettings](../0070-env-var-overrides-appsettings/)). Дублікат
усередині файлу кричить; дублікат між файлами шепоче - і саме шепіт відвантажує
неправильні числа.

## 🎓 Поглиблений нюанс

- **Перевірка нечутлива до регістру.** Ключі конфігурації порівнюються без урахування
  регістру, тож `"MaxConnections"` і `"maxconnections"` в одному об'єкті теж колізять і
  кидають - для провайдера це той самий ключ.
- **JSON-масиви - це під капотом індексовані ключі, тож вони не можуть «дублюватися».**
  `[ "a", "b" ]` стає `:0`, `:1`; немає способу написати той самий індекс двічі, тому
  списки не б'ються об цю помилку так, як іменовані члени об'єкта (див.
  [0080-env-array-needs-indexed-keys](../0080-env-array-needs-indexed-keys/)).
- **Коментарі й висячі коми дозволені; дубльовані ключі - ні.** Провайдер терпить
  JSONC-зручності (`//`-коментарі, висячі коми), тож файл може виглядати поблажливим і
  все одно бути відхиленим за єдине, у чому він суворий, - повторений ключ.

## 🔎 Як знайти у своїй кодовій базі

- Коли деплой кидає `InvalidDataException: Failed to load configuration from file
  '...'`, одразу читай `InnerException` - він називає дубльований ключ і перетворює
  полювання «чому не вантажиться конфіг» на однорядковий фікс.
- Грепни `appsettings*.json` (і будь-який кастомний JSON-конфіг) на ключі, що
  з'являються двічі в одному об'єкті, особливо навколо свіжих merge-конфліктів чи
  вставлених блоків.
- Додай крок лінту дубльованих ключів чи валідації JSON-схеми в CI, щоб пошкоджений
  файл валив пайплайн, а не продовий старт.
- Використовуй `appsettings.{Environment}.json` для оверрайдів, а не повторюй ключ в
  одному файлі - між файлами повторений ключ легітимно заміняє; усередині файлу він
  крашить.

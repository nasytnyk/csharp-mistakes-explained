# #0082 - Null, що пішов у else

## 💥 Симптом

Брама згоди, feature-flag, перевірка «заблокований» - написані як одна умова з
двома результатами - тихо пропускають не ту групу. Ті, хто *відмовився*, коректно
виключені, ті, хто *погодився*, коректно включені, а ті, кого ніхто не питав - чий
прапорець досі `null` - тихо опиняються на дозвільному боці. Ні винятку, чистий
прогін, і маркетингова розсилка щойно пішла тим, хто ніколи не погоджувався її
отримувати.

## 🔍 Проблемний код

```csharp
// MarketingConsent це bool?: true = погодився, false = відмовився, null = не питали
foreach (var user in users)
    if (user.MarketingConsent != false) // 💥 null != false це true - «невизначеному» шлють
        Send(user);
```

## 🧠 Що насправді відбувається

`bool?` має **три** значення - `true`, `false` і `null` - але `if`/`else` має лише
дві гілки, тож один із трьох станів мусить тихо злитися з іншим. `!= false` істинне
і для `true`, *і* для `null`: порівняння підіймається до nullable-логіки,
`null != false` дає `true`, і невизначений користувач іде тим самим шляхом, що й той,
хто погодився. Код читається як «усі, хто не відмовився», але `null` і не
*погоджувався* - його просто не питали, а двобічна перевірка не має куди подіти «не
знаю», окрім однієї з двох реальних гілок.

Хибне переконання - що прапорець це так/ні, тож `!= false` означає «так». З nullable
прапорцем є два способи бути «не false» - справді true й ще не вирішено - і вони
зазвичай вимагають протилежного поводження: згода, яку ти мусиш *мати* до дії; блок,
який ти мусиш *зняти* до дозволу. Перевірка на негатив (`!= false`, `== false`,
`!flag`) кладе `null` на той бік, що є дефолтним, а для дозволів цей дефолт майже
завжди небезпечний: невідома згода трактується як згода, невиставлене «перевірений»
проходить як перевірений, відсутнє «заблокований» читається як не заблокований.

## ✅ Виправлення

Перевіряй той єдиний ствердний стан, який тобі справді потрібен, щоб `null` і `false`
обидва падали на безпечний бік.

```csharp
foreach (var user in users)
    if (user.MarketingConsent == true) // лише явне «так» кваліфікує
        Send(user);
```

Повна версія в [Good.cs](Good.cs); помилка - у [Bad.cs](Bad.cs).

| Підхід | Коли він доречний |
|---|---|
| Перевіряй `== true` (чи `== false`) | Дефолтне правило - назви точний стан, що дає дію, і вимагай його, щоб `null` ніколи не їхав разом зі ствердним. |
| Обробляй усі три стани явно | `null` потребує *власної* поведінки (спитати знову, у чергу на розгляд, залогувати) - `switch { true => ..., false => ..., null => ... }` змушує вирішити, а компілятор помітить пропущену гілку. |
| `flag ?? false` / `GetValueOrDefault()` | Ти справді хочеш «невідоме означає ні» - згорни до звичайного `bool` навмисне, в одному видимому місці, а не лишай ліфтований `!=` вирішувати тихо. |
| Зроби стан non-nullable | Значення має бути завжди відомим на момент перевірки - розв'яжи його на межі (обов'язкове поле, дефолт у міграції), щоб третій стан не дійшов до цього коду. |

## 😈 Ще гірший родич

Розіслати невизначеним - це проблема відповідності; та сама форма, що охороняє
*доступ*, - це вже безпека. `if (user.IsBlocked == true) Deny();` виглядає
непробивним, а `null` `IsBlocked` - рядок, змігрований до появи колонки, користувач,
якого risk-перевірка не оцінила - не `== true`, тож проходить повз гард і його
впускають. І nullable-трьохзначна логіка ще дивніша всередині булевої алгебри:
`null && false` це `false`, але `null || true` це `true`, а `!null` це досі `null` -
тож складений гард на кшталт `if (!(a || b))` може дати `null`, який `if` трактує як
`false`, тихо забираючи else. Баг ніколи не в тому, що прапорець мав неправильне
значення; він у тому, що «немає значення» *було* значенням, а двобічна перевірка не
мала куди його чесно подіти.

## 🎓 Поглиблений нюанс

- **Порівняння ліфтуються, а не кидають.** `null != false` не вибухає - оператори
  `==`/`!=` на `bool?` ліфтовані повертати звичайний `bool`, тож помилка чисто
  компілюється й тихо працює. Це `null`, вжитий *безпосередньо* в `if` (`bool?` там,
  де треба `bool`), компілятор відхиляє - саме тому люди хапаються за `!= false` і
  повертають баг.
- **`==`/`!=` - єдині ліфтовані оператори, що лишаються двозначними.** Логічні
  оператори йдуть трьохзначною (Kleene) логікою й можуть *породити* `null`
  (`null & true == null`), тоді як `==`/`!=` завжди повертають звичайний `bool`.
  Змішування двох родин в одному виразі - це те, як гард тихо розв'язує `null` у
  `false`.
- **`GetValueOrDefault()` для `bool?` дефолтиться в `false`.** Зручно, але це
  невидимо закладає «невідоме = ні»; обирай його лише там, де така політика навмисна
  й очевидна, а не як рефлекс, щоб заглушити nullable-попередження.

## 🔎 Як знайти у своїй кодовій базі

- Грепни `!= false`, `== false` і `!`, застосований до `bool?`-членів (згода,
  `IsVerified`, `IsBlocked`, `IsActive`, feature-flag), і спитай, що має статися,
  коли значення `null` - якщо відповідь відрізняється від гілки `false`, це той баг.
- Дивись особливо на брами дозволів і відповідності: будь-де, де «невідоме» має
  трактуватися як *відмова*, а перевірка виключає лише явний `false`.
- З боку симптомів: дії, виконані для записів, які ніколи явно не вмикали, користувачі
  в групі, до якої не приєднувалися, гарди, що проходять для щойно змігрованих чи
  недоонбоарджених рядків, чиї прапорці досі null.
- Обирай `== true` для «має бути ствердно так», явний трьохбічний `switch`, коли
  `null` має власне значення, чи non-nullable поле, розв'язане на межі, щоб третій
  стан не дійшов до рішення.

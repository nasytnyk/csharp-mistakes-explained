# #0078 - Транзакція, що відкотила саму себе

## 💥 Симптом

Записи виконались, винятку не було, процес вийшов із кодом `0` - а рядків у базі
немає. Код вставки просто ось тут, логи кажуть, що він відпрацював, а звірка
показує недостачу. Те, що виглядає *найбезпечнішим* у методі - `using`, у який ти
загорнув транзакцію, щоб вона ніколи не «протекла», - і є тим, що викинуло роботу.

## 🔍 Проблемний код

```csharp
using (var tx = db.BeginTransaction())
{
    tx.Insert("INV-1001", 149.99m);
    tx.Insert("INV-1002", 200.00m);
    // ... забув tx.Commit()
} // 💥 вихід із блоку робить Dispose незакоммічена транзакція -> rollback
```

## 🧠 Що насправді відбувається

Контракт транзакції - *закоммітити або відкотити*, і `Dispose` мусить обрати щось
за тебе, бо лишити транзакцію відкритою означало б тримати блокування вічно. Кожна
`IDbTransaction` (ADO.NET, EF Core, Dapper) розв'язує незакоммічену транзакцію
єдиним безпечним способом: робить **rollback**. Тож закривальна дужка твого `using`
не просто звільняє хендл - вона ухвалює рішення про твої дані, і рішення для «ти не
викликав `Commit`» - «викинути все».

Хибне переконання: «`using` гарантує прибирання, тож загорнути транзакцію - це
безпечно». Загорнути її *правильно* - транзакцію треба dispose-ити. Пастка в тому,
що для транзакції dispose - це не нейтральне прибирання, як закриття файлу; це
семантичний rollback. Пропустив `Commit` - і доданий тобою конструкт безпеки стає
тихим `DELETE` усього, що зробив блок: без помилки, без лога, з чистим виходом, а
втрата випливає лише коли хтось прочитає дані назад.

## ✅ Виправлення

Закомміть усередині блоку, поки транзакція ще відкрита, щоб `Dispose` уже не мав
чого скасовувати.

```csharp
using (var tx = db.BeginTransaction())
{
    tx.Insert("INV-1001", 149.99m);
    tx.Insert("INV-1002", 200.00m);
    tx.Commit(); // коміт до закриття блоку; Dispose тепер нічого не робить
}
```

Повна версія в [Good.cs](Good.cs); помилка - у [Bad.cs](Bad.cs).

| Підхід | Коли він доречний |
|---|---|
| `Commit()` останнім рядком блоку | Звичайний шлях - підготуй роботу, закомміть, тоді хай `Dispose` звільнить (уже закоммічену) транзакцію. |
| Commit-or-throw, ніколи не «випасти» з кінця | Будь-який блок із раннім `return`/`continue`/гілками - переконайся, що *кожен* шлях або коммітить, або свідомо кидає, щоб жоден не вийшов, зробивши роботу без коміту. |
| Хелпер, що коммітить на успіху, відкочує на винятку | Коли патерн повторюється - `db.InTransaction(tx => { ... })`, що коммітить при нормальному поверненні й відкочує на винятку, тож викликачі не можуть забути. |
| `TransactionScope` з `scope.Complete()` | Ambient/`System.Transactions` код - та сама форма, та сама пастка: забув `Complete()` - dispose scope робить rollback. |

## 😈 Ще гірший родич

Тут rollback принаймні скасовує *повну* одиницю роботи - ти втрачаєш усі три вставки
разом, що бридко, але консистентно. Гидкіший варіант - блок, що коммітить на одних
шляхах і ні на інших: ранній `return` після першої вставки, але до `Commit`, чи
`continue` в циклі, що пропускає коміт для певних рядків, лишає тебе з *частковою*
історією записів, де частина транзакцій закоммічена, а частина тихо відкочена в тому
самому прогоні - реєстр тепер внутрішньо неконсистентний, і оскільки ніщо не впало,
немає метрики невдалих запитів, що вказала б на діру. Дзеркальна проблема теж кусає:
транзакція, яку ти забув *dispose-ити взагалі*, шкодить навпаки - тримає блокування
відкритими, блокуючи кожного іншого писача, поки з'єднання не заберуть назад.

## 🎓 Поглиблений нюанс

- **Rollback-on-dispose - документована поведінка, не випадковість.** `IDbTransaction`
  в ADO.NET, `IDbContextTransaction` в EF Core і `TransactionScope` - усі
  специфікують, що dispose без коміту робить rollback. Це безпечний дефолт - баг у
  тому, щоб покладатися на безпечний дефолт задля *збереження* твоїх даних.
- **`SaveChanges` - це не `Commit`.** В EF Core `SaveChanges()` усередині явного
  `using var tx = ctx.Database.BeginTransaction()` пише рядки, але не коммітить
  транзакцію; без `tx.Commit()` dispose усе одно відкотить усе, хоча `SaveChanges`
  відзвітував про успіх і повернув кількість рядків.
- **Шлях із винятком *має* відкочуватися - це фіча.** Мета не «ніколи не відкочувати»,
  а «відкочувати лише коли ти цього хотів». Фікс змушує *успішний* шлях коммітити
  явно, лишаючи `Dispose` відкочувати саме ті шляхи, що кинули - для цього транзакція
  й існує.

## 🔎 Як знайти у своїй кодовій базі

- Грепни `BeginTransaction` і `TransactionScope`, тоді перевір, що кожен
  результівний `using`-блок містить `Commit()` / `Complete()` на успішному шляху - і
  що жоден ранній `return`/`break`/`continue` не перестрибує через нього.
- Пильнуй блоки, що кличуть `SaveChanges()` (EF Core) усередині явної транзакційної
  `using`, але ніколи `tx.Commit()` - рядки ніби зберігаються, тоді зникають на
  dispose.
- З боку симптомів: записи, що «не тримаються», недостачі у звірці без помилок у
  логах, дані, присутні в пам'яті застосунку під час запиту й відсутні після, і баги,
  що зникають, щойно додаєш `Commit`, який вважав зайвим.
- Обирай транзакційний хелпер (`InTransaction(...)` / метод репозиторію), що коммітить
  при нормальному поверненні й відкочує на винятку, щоб окремі місця виклику взагалі
  не могли забути коміт.
